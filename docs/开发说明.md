本文面向需要构建、调试或扩展 SPW Lyrics 的开发者。日常使用见 [使用说明](使用说明.md)，故障处理见 [常见问题](常见问题.md)。

## 环境与构建

### 技术栈

| 项目 | 当前配置 |
| --- | --- |
| 插件 | Kotlin `2.4.20` / JVM 25 |
| SPW Workshop API | `0.1.0-dev23` |
| 工具界面 | Salt UI `3.0.0-beta03` / Compose Desktop `1.12.2` 编译接口，复用宿主 Compose/Skiko 与 JVM |
| 构建 | Gradle Wrapper `9.8.0` |
| 插件版本 | `3.1.0` |

当前版本面向采用 Workshop API dev23 / JVM 25 的 SPW 1.19.0，不兼容旧版 Workshop API。

### 构建

需要 JDK 25。在仓库根目录运行：

Windows（PowerShell）：

```powershell
.\gradlew.bat test plugin --no-daemon
```

Linux（Bash，无需为脚本设置执行权限）：

```bash
bash ./gradlew test plugin --no-daemon
```

插件包输出到：

```text
build/libs/spw-lyrics-3.1.0.spmod
```

工具界面在 SPW 主窗口及其 JVM 内运行。安装包携带 Salt UI 和必要依赖，复用 SPW 提供的 Compose、Skiko、Kotlin、JNA 和平台原生库。JNA 及其平台扩展不随插件打包，避免其原生资源缓存占用旧插件 JAR，阻止 Windows 更新时移动目录。

## 架构与歌词处理

### 代码结构

核心代码按职责拆分，而不是按歌词平台堆在播放回调里。主要数据流为 **Provider → 匹配与选择 → 缓存 / 输出 → SPW 与 AMLL 接收端**。

| 目录 | 主要职责 |
| --- | --- |
| `domain` | 曲目查询、歌词候选、歌词文档、质量和匹配数据模型 |
| `codec` | 歌词解析、SPW 输出，以及元数据编辑标签页的 TTML / LRC / 增强 LRC / SPL 转换 |
| `provider` | AMLL、QQ、酷狗、网易云等来源适配 |
| `application` | 搜索、选择、缓存协调和批量处理 |
| `storage` | 歌词缓存、手动选择、本地数据布局和音频标签读写 |
| `integration` | SPW Workshop API、设置、播放回调和窗口接入 |

新增歌词来源时，优先实现独立 Provider 和格式适配，不要把平台请求逻辑直接写入播放回调或界面层。

### 歌词处理流程

自动搜索的大致流程为：

1. 各 Provider 搜索歌曲并返回统一的候选元数据。
2. 匹配器结合歌名、歌手、专辑和时长筛选候选，并排除明显的 Live、Remix、伴奏等冲突。
3. 下载候选歌词后再按实际内容判断是逐字、逐行还是普通歌词。
4. 根据用户填写的类型与来源顺序选择，支持类型优先和来源优先。
5. 保留所选来源自带的翻译和音译。
6. 缓存解析后的文档及 SPW 编码；TTML 同时保留未经修改的完整 XML。播放时复用编码，存在单曲延迟时重新编码，并请求宿主刷新；原始 TTML 另外提供给原生接收器。

自动播放采用渐进式结果：第一个通过匹配检查且符合选择设置的结果立即提供，后续每次来源完成后重新比较，整体搜索期限为 20 秒。找到更好的歌词时再次更新缓存和当前显示，手动选择不会被自动升级覆盖。

`LyricsPrecache` 在默认替换策略下延迟启动，按当前歌曲在曲库中的位置依次准备后续最多 3 首歌曲，每 5 分钟按需更新曲库快照；dev23 未公开播放队列，不能据此预测随机播放。`LyricsResolutionTasks` 统一管理播放和预缓存的同曲任务，预缓存使用独立的单曲工作线程和 Provider 线程池，播放切入时复用任务。切歌、策略变更和手动选择会中断过期任务，并在写缓存前检查任务及选择状态。

缓存的内存命中不持有磁盘操作锁，磁盘读写按歌曲分组加锁；手动选择和未设置选择的状态也保留有限的内存缓存。旧 TTML 缓存首次读取时补齐 SPW 编码。本地歌词检查按音频、同名 `.lrc` 和 `.ttml` 的大小与修改时间复用结果，文件变化后重新读取。

`LyricsPreferences` 是一次解析的不可变快照，`LyricsPreferenceInput` 解析可编辑列表；缺失项不参与自动选择，错误或重复项拒绝整次排序更新。默认类型为 `逐字 > 逐行 > 普通`，来源为 `AMLL > QQ > 汽水 > 酷狗 > 网易 > Apple Music > LrcShare > MusicBrainz`，最后一项只参与手动元数据搜索。`LyricsSelectionPolicy`、渐进式提前结束条件及后台升级都使用同一快照。自动缓存记录快照标识，设置变化后旧缓存和迟到结果不覆盖新选择；单曲手动选择保留。

## 歌词来源与元数据

### 歌词来源

| 来源 | 获取方式 | 主要格式 / 数据 |
| --- | --- | --- |
| AMLL TTML DB | 缓存并查询索引，命中后下载单个 TTML 文件 | TTML、逐字、对唱、背景歌词 |
| QQ 音乐 | 搜索歌曲 ID 后获取并解码歌词 | QRC / LRC、逐字、翻译、音译 |
| 酷狗音乐 | 通过歌曲 Hash 查找歌词候选，再下载并解密 KRC | KRC、逐字、内嵌翻译 |
| 网易云音乐 | 搜索歌曲后优先请求新版歌词接口，失败时回退兼容路径 | YRC / LRC、翻译、音译 |
| 汽水音乐 | 搜索歌曲、SEO 详情及分享页回退 | 逐字、逐行、翻译及词曲信息 |
| Apple Music | iTunes 公共目录搜索，PaxSenix 第三方歌词接口 | 目录元数据；歌词取决于接口可用性 |
| LrcShare | 用户 API Key 获取目录会话，再查询歌曲和歌词 | 优先保留完整 TTML，也支持结构化歌词行 |
| MusicBrainz | recording / release 搜索与 work 详情 | 仅元数据；请求串行且间隔至少 1.1 秒 |
| SPW 本地歌词 | 不属于网络 Provider；本地 TTML 在播放回调中直接转换，其余内容交还 SPW | 支持同名 `.ttml`、内嵌 TTML 和内容为 TTML 的同名 `.lrc`；普通内嵌歌词及 `.lrc` 由 SPW 处理 |

#### 在线接口与失败隔离

QQ 音乐、酷狗音乐和网易云音乐使用的是客户端或网页侧可访问的网络端点，并不是平台承诺长期稳定的开发者 API。接口地址、参数或返回结构发生变化时，对应 Provider 可能需要更新；单个来源失败不应阻止其他来源继续工作。

#### AMLL 索引管理

AMLL 只持久化索引并在命中后下载单个 TTML 文件，不会在运行时遍历整个歌词仓库。索引有效期为 6 小时，刷新失败后至少间隔 5 分钟再试；搜索时发现索引过期，有可用缓存则先返回本地结果并在后台更新，没有可用缓存时才等待下载。停用插件时取消后台刷新。

索引检索保留全部歌名和专辑别名，支持部分词、单字和括号内关键词；手动搜索先按输入关键词排序，再限制候选数量，不会被当前播放歌曲的外部 ID 锁定。自动匹配仍需通过原有的歌曲信息和版本校验。

#### QQ 搜索与网络回退

QQ 搜索由 `QqSearchProtocol` 负责 Lite、Mobile、Desktop 和兼容请求的协议与结果解析，检查 HTTP 和业务状态，展开同曲分组、去掉搜索高亮标记并去重。`QqSearchClient` 优先请求 Lite，等待 900ms 仍无有效候选时启动下一个接口；失败或空结果立即尝试下一个，整体等待上限为 5 秒，得到候选或取消后取消其他请求。有效非空结果在内存中缓存 2 分钟，最多 64 个关键词；数量限制在取缓存后应用，失败和空结果不缓存。JSON POST 与 GET 一样，在 TLS 握手失败时可使用已有公共 DNS 兼容路径，保留原始主机名的 SNI 和证书校验。插件停用时关闭 QQ 请求执行器。

#### 酷狗搜索与元数据导入

酷狗使用签名搜索并展开同曲分组，失败后回退兼容接口，避免只保留分组顶层的混音版。

详情请求独立于歌词搜索：`CandidateMetadata` 统一结构化字段，`MetadataEnrichment` 为选中候选提供最多 128 项的 7 日内存缓存和 2 分钟失败冷却。QQ、酷狗、网易、汽水及 MusicBrainz 的详情只在导入元数据时补充；私有 ID 保留在候选上下文，不成为可写标签。`OnlineMetadataImport` 负责字段选择、补空与覆盖规则，界面只将结果应用到草稿，空值不覆盖已有内容。文件写入继续使用原有暂存、回读和回退事务；多值标签逐项追加，避免标签库只接收第一个值。

## 宿主集成与 TTML 互通

### SPW 集成

使用 `com.xuncorp.spw.workshop` `0.1.0-dev23` Gradle 插件生成 `.spmod` 安装包，并申请：

- `library-read`
- `class-transform`：主窗口顶部入口、播放器菜单、页面和导航 Hook

曲库通过 `WorkshopApi.library.getAllTracks()` 读取，歌曲时长来自 `MediaItem.duration`。曲库 ID 只用于当前插件会话内补齐回调信息和校验 TTML 接收对象，不写入持久缓存或缓存键。

歌词回调只使用已有的曲库元数据；缺失时长由解析工作线程查询补齐，最多等待 2 秒，不阻塞缓存命中。

手动搜索通过 `WorkshopApi.playback.getCurrentMediaItem()` 获取当前歌曲。主窗口顶部入口默认打开批量管理；播放器“更多”菜单提供手动搜索和元数据编辑入口。

#### 当前歌词刷新

dev23 仍没有正式的“重新加载当前歌词”接口，因此自动刷新保留 `ReflectiveLyricsRefreshBridge`，通过 `PlaybackService` 的歌词加载器按当前歌曲 ID 请求重载。宿主拒绝已过期的歌曲 ID，避免切歌后刷新错对象。这个位置是 SPW 版本升级后最需要优先验证的部分之一。

### 原始 TTML 互通

`LyricsOutputRouter` 统一处理本地读取、缓存命中、自动获取、手动选择、质量升级和延迟更新。`JmxTtmlReceiver` 通过 JVM 平台 MBeanServer 调用 [AMLL into SPW 的协议 1](https://github.com/GaBoron/AMLL-into-SPW/blob/main/docs/TTML互通.md)，只依赖 JDK，不加载对方 JAR，也不启动网络服务。

#### 接收协议

接收器名为 `io.github.gaboron.amllspw:type=TtmlReceiver,version=1`。后台输出线程检查 `ProtocolVersion == 1`、`Active == true`，调用 `submitTtml(String trackId, String audioPath, String ttml, long offsetMs)`；返回 `true` 表示原始 TTML 已接收，普通 SPW 输出仍保留，供宿主及灵动词岛等插件读取。协商期间、拒收或异常时也继续提供普通输出。参数使用宿主原始 ID 和路径，XML 不修改时间，单曲偏移单独传递，不包含 SPW 全局偏移。

#### 状态跟踪与撤回

输出线程每 500 毫秒重新检查当前歌曲和接收器状态，并监听 MBean 注册变化；接收器未变化时不重复提交或解析。启用顺序、权限恢复和接收器重新注册均可触发重提，停用或撤权不影响普通输出。选择与偏移各有代次校验，切歌后的迟到结果不能替换新选择；撤回外部选择、改用非 TTML 歌词和插件关闭时调用 `clearTtml`。

#### 缓存与回退

原始 XML 随 `LyricsDocument` 缓存，同时保留普通 SPW 输出所需的解析文档及编码。缺少原始 XML 的旧 TTML 缓存会按需失效并重取，其余缓存和手动匹配格式保持兼容。AMLL into SPW 自己读取的本地 TTML 优先，接口偏移只作用于接口提交的结果。

## 界面与批量处理

### 批量处理

批量处理和正常播放共用同一套 `LyricsResolver` 与歌词缓存，但不触发播放刷新，也不会写回 SPW 音乐库。

`integration/batchui` 实现批量管理标签页。`BatchProcessingController` 在后台串行执行命令、读取快照并保留歌曲勾选状态，Compose 列表和任务概览负责展示。`BatchAutoFollow` 只管理列表的视图行为：跟随正在搜索的歌曲，真实指针或键盘操作后暂停，空闲 3 秒恢复；自动滚动本身不会重置暂停计时。曲库读取与处理由 `LyricsBatchProcessor` 完成；可选的 `BatchMetadataWriter` 按已确认的字段和补空/覆盖模式，复用 `FileAudioMetadataStore` 的校验与回退事务逐文件保存。网络解析可按录音共享，音频标签事务按各自路径执行。逐曲编辑使用独立草稿 Controller，开始批量任务前先处理该草稿。

#### 并发、状态与结果复用

当前最多同时处理 3 首歌曲。相同录音会根据曲名、歌手、专辑和近似时长复用解析结果，减少重复网络请求。进度由解析层报告，界面只负责选择范围和展示状态。

关闭批量页面后，任务继续运行；重新打开会显示当前状态。停用插件时会关闭歌词管理页面并停止后台任务。

### 手动搜索与歌词延迟

`integration/manualui` 通过 `ManualSearchOperations` 调用应用层。`ManualSearchController` 管理异步请求和页面状态；搜索结果、预览、来源筛选和延迟编辑各自使用独立的 Compose 组件。共享的 `integration/composeui` 提供 Salt UI 主题与控件，`integration/workspace` 提供原生分组、标签、菜单和短窗口滚动视口。

#### 搜索状态与异步结果

`ManualLyricsSearch` 先返回候选元数据；`ManualCandidateInspector` 随后在后台并行读取候选歌词，逐项更新实际类型，不阻塞列表操作。预览与类型识别共享进行中的请求及解析缓存，应用时复用文档；搜索条件变化或关闭页面时取消过期识别，迟到结果按搜索代次丢弃。搜索协调各词源的实际状态，区分正常空结果、接口失败与期限超时；Provider 校验业务状态和响应结构，失败不会再作为成功的空列表返回。AMLL 的本地索引查询与索引更新分别报告；后台更新完成可继续通知当前搜索，更新失败仍保留旧索引。Controller 按搜索代次接收状态，关键词、来源或歌曲变化后拒绝迟到结果，不增加定时网络探测。

#### 播放器菜单接入

播放器菜单通过 `HostPlayerMenuDiscovery` 独立定位宿主的普通菜单构建方法，再用公开 `hookMethod` 在构建完成后追加手动搜索和元数据编辑两个原生菜单项。按参数类型定位菜单作用域和弹出状态，不依赖混淆后缺失的参数名；保留原有菜单构建和渲染。每次打开管理页前调用宿主导航的收起播放器动作，使展开的歌词播放页让出管理页面；已有管理会话也执行此动作。菜单发现或安装失败会提示，并保留顶部歌词管理入口。停用或撤销类变换权限时释放菜单注册。

#### 管理页面与状态

`integration/workspace` 持有搜索、元数据、批量任务及打轴会话状态。首次进入标签时加载相应数据，标签切换不重建 Controller，并通过可保存状态容器保留各页的排序、滚动和子标签。元数据未保存确认统一在会话层处理，关闭会话才释放界面工作线程。页面底层透明，列表和编辑区使用 Salt UI 原生分组，输入框共用单层表面和焦点边框；应用、导入和写入操作放在内容下方，继续为播放条留白。横向标签使用带方向的滑动和连续下划线，侧栏及导航保留控件位置的连续过渡。`HostPopupMaterialDiscovery` 定位宿主弹出菜单使用的模糊材质函数，选择框复用宿主材质与相关设置；材质发现失败时保留普通菜单。`LyricsDocumentPreview` 为搜索与元数据页共用，统一显示左右声部、背景人声、翻译和音译；手动搜索在后台读取原始 TTML 的主唱定义。

#### 主窗口 Hook 与动态发现

`integration/hostui` 从宿主实现类的代码来源读取字节码，用 JVM 25 Class-File API 建立方法签名、字段和调用关系索引。导航根、标题栏控件、调用位置和导航操作通过联合结构约束发现，不固定宿主方法名、混淆类名、安装路径或版本表。候选必须唯一，准备失败时清理本次注册并报告原因；每次启用重新扫描。页面和入口通过 Compose Hook 接入，普通方法 Hook 用于导航操作及离开确认；宿主歌词面板展开时，返回操作先交给宿主收起面板。宿主页面持续组合以保留状态，歌词管理打开时隐藏其绘制和语义，避免透明背景透出原页面内容；关闭后恢复原页面，不写入宿主导航栈。

#### 歌曲身份校验与延迟

搜索、预览、缓存写入和刷新都在后台执行；关闭页面或更换候选后，过期结果不会更新当前界面。应用歌词、切换策略和保存延迟均校验歌曲身份，切歌后需要刷新页面中的当前歌曲。

延迟按歌曲独立保存在本地，范围为 -60000 到 60000 毫秒。`LyricsTimingOffset` 在输出时同时移动行和逐字时间，早于歌曲起点的时间限制为 0；歌词文本、翻译及缓存中的原始时间轴不变。自动升级、更换来源和恢复自动匹配不会重复叠加延迟。插件转换的本地 TTML 同样应用延迟；交还 SPW 加载的普通本地歌词不受影响。

## 网络与本地数据

所有在线来源都先使用歌曲元数据进行搜索，只在需要检查或使用候选时下载歌词正文。本地 TTML 转换只读取外置歌词或音频中的歌词标签；元数据编辑页面在用户点击写入时修改所选文件；批量管理在用户确认字段与模式后执行所选音频文件的标签事务。标签事务使用系统临时目录，写入和读回校验失败时回退原文件，结束后清理事务文件。不上传音频文件，也不要求用户登录音乐平台账号。

Windows / Linux 的缓存与单曲延迟位置见 [使用说明](使用说明.md#本地缓存)。两者分别保存，清理缓存不会重置延迟设置。

用户手动选择和“切回本地歌词”也会保存到本地，用于覆盖全局自动策略。
